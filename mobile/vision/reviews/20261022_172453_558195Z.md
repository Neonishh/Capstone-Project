# Settings run review and implemented follow-up

Reviewed local artifacts from `mobile/logs/vision/20261022_172453_558195Z/`.
This review describes recorded behavior and code changes, not a new live benchmark.

## Findings

- 40 exploration actions, 22 reported UI changes, 18 actions without detected effect.
- 11 generated cases, 9 passing replays, 2 failures (81.8%).
- TC004 and TC007 both assert `Checking info…`. Both failures report the expected
  text missing while the expected activity matches. This establishes an unstable
  oracle, not a demonstrated Settings defect.
- TC004/TC007 duplicate sign-in intent. TC008/TC010 duplicate the account-help
  behavior. Position and viewport changes were being included in behavior identity.
- TC001 only checks a Back label and Search activity, not search functionality.
- TC011 checks an empty-email validation message, but was generated incidentally
  while wandering through Google authentication, not from a reviewed requirement.
- Most later actions are Google account screens or their help dialog rather than
  distinct Android Settings features. Keyboard/layout variations inflate coverage.
- Model configuration records `provider: openai`, but `model: null`. This prevents
  confirming the actual model from the run record alone.
- The merged perception discarded accessibility class/package information,
  including in the branch where an OCR detection overlapped a native control.

## Plan implemented

1. Bound exploration to the chosen foreground package, with explicit additional
   packages via `--allow-package`. Android Settings also permits its Google search
   companion. Other external flows cause a return to the starting activity before
   another model call. Record package boundaries in memory.
2. Use stable control labels/IDs for attempts; ignore layout coordinates when a
   label or ID is available. Exclude clocks, summaries, keyboard packages, and
   editable text from screen fingerprints. Preserve class/package through merging.
3. Track meaningful progress, recover after three consecutive ineffective actions,
   and cap visits to a screen between recoveries. Preserve attempted controls when
   restarting so the next branch can be explored.
4. Poll accessibility until two matching observations (bounded at four seconds).
   Do not ask the model to act on an unsettled/loading screen. Capture the settled
   screenshot and reject unresolved loading destinations when generating cases.
5. Exclude loading text, generic navigation labels, long descriptive paragraphs,
   and numeric-only status strings from automatically generated text assertions.
   Search entry can instead assert the presence of its unique editable control
   and expected activity. This checks entry, not actual query results.
6. Deduplicate equivalent control/action/outcome behaviors without screen hashes or
   coordinates. Keep distinct labels even when list rows share a resource ID.
   Preserve navigation required by different behavior tests.
7. Write `generation_review.json`, model name, scope, coverage, and explicit
   exploration outcome. Fatal exploration/finalization errors return nonzero.
   Database execution completion retains its existing meaning: all cases have an
   outcome; it does not mean all assertions passed or exploration succeeded.

offline candidates were not replayed and have no new pass-rate claim.
